How I Work

Problem Framing

I start from the customer problem and the constraint, not the feature request. My background in behavioral sciences and education is the real leverage here: it shapes how I read user behavior, separate what people say from what they do, and turn a vague goal into a problem statement a team can build against. I write the tradeoffs down — customer value, implementation cost, operational trust — so a decision stays reviewable instead of being remembered differently by everyone a month later.

Launch and Delivery

I scope launches as reviewable increments with an explicit quality bar, then drive them across the functions that have to agree. I have owned release readiness on consumer apps with large audiences, which is why I treat instrumentation, observability, and rollback paths as product requirements rather than engineering overhead. I define the KPIs before launch, build the dashboards that watch them, and use that data to decide what ships next.

Technical Judgment

I carry enough depth to keep engineering tradeoffs honest. I have architected native mobile clients, shared cross-platform cores, SDKs consumed by external developers, and the API and authentication boundaries between them — so I can tell a stakeholder what a constraint actually costs, question an estimate without guessing, and write a spec that survives contact with the codebase. I use AI-assisted tooling pragmatically, around solid systems and people first.

Community Booking Platform

Community Booking Platform is collaborative OpenForm Studio work with Keys 4 Community (K4C), a nonprofit serving the Triangle area, focused on turning message-and-spreadsheet scheduling into a trustworthy booking workflow. It highlights product and architecture judgment around clear participant roles, server-enforced scheduling rules, administrative oversight, notification workflows, and a shared API contract that supports web delivery now and native clients later.

Public repository: Community Booking Platform

Product judgment:

  • Framed the problem before the solution: the nonprofit was coordinating bookings through group messages and a spreadsheet, so the real failure mode was not a missing calendar but unclear ownership of who had confirmed what.
  • Defined participant roles, administrative oversight, and notification workflows as the product surface, then pushed the scheduling rules into the API so a client could not bypass them.
  • Chose web-first delivery against a native-ready API contract: a scope decision that gets the nonprofit a working product now without foreclosing native clients later.
  • Worked from booking failures observed with the operator rather than designing against a generic calendar abstraction.

Product and technical focus:

  • Web-first delivery with a native-ready architecture, server-owned workflow state, role-based access, scheduling constraints enforced by the API, transactional notifications, OpenAPI contract discipline, Next.js/React/TypeScript, FastAPI/Python, PostgreSQL, Redis-backed jobs, OIDC-oriented auth, and Kotlin Multiplatform planning for later native clients.

Turn-Based Mobile Game

Turn-Based Mobile Game is production-bound OpenForm Studio mobile game work in the Dots and Boxes family, planned first for iOS with Android following on the same shared core. The product direction combines short turn-based matches, native mobile UX, and a model-backed match loop where structured board state is encoded for an LLM to validate human turns and generate the computer’s next move.

The work emphasizes product definition, cross-platform delivery judgment, and mobile architecture choices that keep the game portable without flattening it into a lowest-common-denominator UI. UIKit and SwiftUI shape the first iOS client, Kotlin Multiplatform owns shared match state, matrix encoding, model adapter boundaries, and apply-after-accept behavior, and dedicated Compose screens remain the Android path.

Public repository: Turn-Based Mobile Game

Product judgment:

  • Defined the product as short turn-based matches with a model-backed opponent, then scoped the first release to iOS so one platform could feel finished rather than two feeling thin.
  • Made a deliberate call about where AI belongs in the product: in the match loop as differentiated gameplay, not as a chat surface, and not as delivery tooling inside the shipped runtime.
  • Protected the Android launch path through shared-core decisions locked early, while keeping dedicated native UI on each platform instead of accepting a lowest-common-denominator interface.
  • Drove the work toward a store-ready release: release preparation, QA, store packaging, and production-readiness review.

Product and technical focus:

  • iOS first with UIKit and SwiftUI, Android follow-on with Kotlin and Jetpack Compose, Kotlin Multiplatform shared core, matrix-based match encoding, model-backed turn validation and opponent moves, fake-model testing, inference timeout/error handling, release preparation, QA, store packaging, and production-readiness review.

Context-Aware AI Integration

Context-Aware AI Integration is production-bound OpenForm Studio native app work that integrates a language model with structured local context so generated output stays grounded in source material. The product direction emphasizes useful AI behavior inside a real mobile workflow, not a generic chatbot surface or a prompt assembled separately by each client.

The work uses an iOS-first path with UIKit and SwiftUI, while keeping Android aligned through a Kotlin Multiplatform shared core and dedicated Compose UI. The shared module owns context assembly, session state, model adapter boundaries, and grounding checks so neither platform UI owns prompt construction, vendor response parsing, or acceptance of ungrounded output.

Public repository: Context-Aware AI Integration

Product judgment:

  • Started from a product requirement rather than a model capability: generated output has to stay grounded in the user’s own source material, or the feature is not trustworthy enough to ship.
  • Turned that requirement into an architectural boundary, with context assembly, session state, and grounding checks owned by the shared core so no client can accept ungrounded output on its own.
  • Specified the failure behavior as part of the product rather than an afterthought: inference timeout, retry, and fallback paths that keep the workflow usable when the model is slow or wrong.
  • Kept product runtime AI separate from AI delivery tooling, in both the architecture and the story told about it.

Product and technical focus:

  • iOS first with UIKit and SwiftUI, Android follow-on with Kotlin and Jetpack Compose, Kotlin Multiplatform shared core, structured local context, model adapter boundaries, grounding checks, inference timeout/retry/fallback behavior, release preparation, QA, store packaging, and production-readiness review.

Transmira

In the early stages of OpenForm Studio, the studio collaborated with Robert Rice, CEO of Transmira, on Omniscape. I was using a different LLC name at the time. It was an early AR product exploration that required turning a novel concept into an investor-facing iOS product build. The core product idea joined location, shared virtual objects, user inventory, and real-world redemption into a mobile AR experience.

My role was to move the idea from concept to a working investor-facing mobile experience. I researched ARKit after WWDC 2017, presented AR/MR/VR trends for prospective clients and the local technology community, and then worked directly with Robert to build a mobile experience suitable for investor conversations.

The product challenge was not only rendering objects in AR. It was making virtual objects behave like shared, location-aware inventory that could be observed by multiple users, moved between locations, and connected to real-world goods. To support that behavior, I built a Firebase backend with simple JSON-oriented data structures and realtime observation, then consumed those updates from the iOS client.

The mobile implementation prioritized validation, speed, and believability over long-term platform polish. Many key behaviors were isolated in a scene-rendering view controller and scene-object subclasses, including GPS coordinate conversion, object placement, inventory behavior, and observable updates from the backend.

Product judgment:

  • Moved a speculative AR concept onto an investor-facing validation path, where the goal was a credible demonstration of the core loop rather than a maintainable platform.
  • Identified the real product challenge as behavior rather than rendering: virtual objects had to act as shared, location-aware inventory, observable by multiple users, movable between locations, and redeemable against real-world goods.
  • Chose validation speed and believability over long-term polish, and documented the maintainability tradeoffs for later product stages instead of leaving them implicit.
  • Connected market storytelling to product behavior, presenting AR/MR/VR trends to prospective clients and the local technology community alongside the build.
